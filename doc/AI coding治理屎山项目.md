下面按你前面的分类，把每一项特征补上一列：**AI code agent 时代的处理策略**。这里按“先理解、再锁定行为、再小步重构、再验证”的思路整理。

### 代码层面特征 + AI agent 应对策略

| 特征       | 典型表现                  | AI code agent 时代怎么做                                                   |
|----------|-----------------------|-----------------------------------------------------------------------|
| 巨型类/巨型方法 | 一个 Service 几千行，职责混杂   | 先让 AI 输出职责拆分图和调用链，再按“提取方法/提取类/抽取接口”拆成原子任务；每次只改一个职责，跑编译和回归测试后再合并。      |
| 命名随意     | `a`、`temp`、`flag1` 等  | 让 AI 基于上下文生成候选命名，但必须人工确认业务含义；避免把“语义不明”的变量改成“看起来正确但实际错误”的名字。           |
| 注释缺失或失效  | 复杂逻辑无说明，或注释与代码不一致     | 让 AI 先生成“行为说明”和“输入输出契约”，再补注释；对关键分支要求 AI 标注假设和风险点，避免把隐性业务规则写丢。         |
| 嵌套地狱     | if-else、for、回调嵌套过深    | 让 AI 识别可提取的分支，转为卫语句、策略类、状态机或表驱动；重构前后必须用等价测试验证分支覆盖。                    |
| 硬编码/魔法数字 | URL、状态值、阈值写死          | 让 AI 扫描常量、魔法值、环境相关配置，收敛到配置中心或常量类；涉及多环境切换时，优先提取为可配置项，而不是继续散落在代码里。      |
| 代码重复     | 相同逻辑复制粘贴              | 让 AI 找出重复代码簇，提出“提取公共方法/公共组件/公共工具类”的方案；合并前确认调用方是否依赖细微差异。               |
| SQL 散落   | 拼接 SQL 散落在业务代码中       | 让 AI 梳理数据访问路径，收敛到 Mapper/Repository 层；对动态 SQL 要求 AI输出参数来源、影响表和潜在注入风险。 |
| 异常处理混乱   | 吞异常、不打印日志、catch 空块    | 让 AI 扫描异常处理模式，统一错误码、日志字段和重试策略；但异常语义必须由人工确认，避免把“业务预期异常”误改成系统错误。        |
| 事务边界不清   | 大事务、业务和数据库操作混杂        | 让 AI 识别事务入口、DB 读写点和外部调用；把远程调用、消息发送、文件操作移出事务；涉及资金、库存、状态机时先补特征测试。       |
| 分层混乱     | VO/DTO/Entity 不分，逻辑纠缠 | 让 AI 生成当前分层现状图，再按“接口契约不变”逐步抽取；每次迁移一层，避免同时改 DTO、Service、DAO 和前端。       |

### 架构层面特征 + AI agent 应对策略

| 特征        | 典型表现                | AI code agent 时代怎么做                                      |
|-----------|---------------------|----------------------------------------------------------|
| 模块耦合严重    | 改一处影响多处             | 让 AI 生成模块依赖图和调用热力图，优先从低风险、低依赖模块开始解耦；必要时采用绞杀者模式，新旧实现并行对比。 |
| 职责不清晰     | 一个类既做业务又发 MQ 又跑定时任务 | 让 AI 识别横切职责，拆成独立组件或事件监听器；拆分前先锁定外部契约，避免把“看似多余”的副作用删掉。     |
| 全局状态滥用    | 静态变量、全局共享状态         | 让 AI 扫描全局可变状态，改为依赖注入或局部状态；对并发相关变量要求 AI标注线程安全风险。          |
| 依赖方向混乱    | 循环依赖、反向依赖           | 让 AI 输出循环依赖链，提出接口抽象、事件总线、适配器层等解耦方案；改动后重新跑依赖检查。           |
| 配置和代码混在一起 | 环境、开关、阈值散落在代码中      | 让 AI 抽取配置项，建立配置清单；对配置变更要求 AI给出影响范围和回滚方式，避免把配置改散。         |

### 开发维护层面信号 + AI agent 应对策略

| 特征       | 典型表现       | AI code agent 时代怎么做                                        |
|----------|------------|------------------------------------------------------------|
| 新人上手极慢   | 文档缺失、流程不清晰 | 让 AI 生成模块说明、调用链、数据流转和启动验证步骤；但要把 AI 产出作为“初稿”，由熟悉业务的人校准。     |
| 团队有修改恐惧症 | 不敢动旧代码     | 先用 AI 生成特征测试和回归用例，把“当前行为”锁住；有安全网后再改，降低心理负担。                |
| 牵一发而动全身  | 小改动引发大范围回归 | 让 AI 评估变更影响面，列出可能受影响的接口、表、定时任务和消息消费者；回归范围由 AI 辅助裁剪，但由人工拍板。 |
| 很难写单元测试  | 依赖太多，无法隔离  | 让 AI 生成测试桩、Mock 和集成测试骨架；对难以隔离的模块先用集成测试/端到端测试兜底。            |
| 需求靠打补丁   | 不断加 if 分支  | 让 AI 识别补丁模式，提出规则表、策略模式、状态机或配置化方案；避免继续用新 if 覆盖旧 if。         |

### 可量化指标 + AI agent 应对策略

| 指标     | 典型表现        | AI code agent 时代怎么做                               |
|--------|-------------|---------------------------------------------------|
| 循环复杂度高 | 分支、嵌套过多     | 让 AI 输出高复杂度函数清单，按风险排序；优先拆解分支最多、变更最频繁的函数。          |
| 函数过长   | 单方法行数超标     | 让 AI 按职责边界拆分为小函数，并生成函数职责说明；每次拆分后跑测试验证等价性。         |
| 嵌套过深   | 超过 3–5 层嵌套  | 让 AI 改写为卫语句、提前返回、策略分发；对状态相关逻辑要求 AI保留原有时序约束。       |
| 代码重复率高 | 相似代码块反复出现   | 让 AI 聚类重复片段，给出统一抽象方案；合并前检查每处细微差异是否属于业务规则。         |
| 注释覆盖率低 | 关键逻辑缺少说明    | 让 AI 补“为什么这么写”的业务注释，而不是只描述代码做了什么；对历史坑点要求 AI标记风险。  |
| 错误处理缺失 | 忽略异常、未处理返回值 | 让 AI 扫描未处理返回值和空 catch，统一补全；但错误语义、重试策略、告警级别需要人工确认。 |
| 模块耦合度高 | 依赖复杂、循环依赖多  | 让 AI 持续生成依赖健康度报告，把解耦纳入迭代任务；每次重构后重新扫描，观察指标变化。      |

使用 AI code agent 时，有一条通用原则：**不要让它一次性重写整个模块，而是让它先画地图、再锁行为、再拆任务、再验证差异。**
尤其要注意，AI 可能会把“难看但有业务含义”的逻辑误判为冗余代码，所以关键模块必须用测试、日志、回放或双跑对账来兜底。

### 屎山治理检查清单

| 检查项        | 怎么做                                      | 验证方式            |
|------------|------------------------------------------|-----------------|
| 生成项目地图     | 让 AI 输出模块结构、调用链、数据流向、外部依赖                | 人工确认关键路径是否遗漏    |
| 锁定当前行为     | 为高频改动模块补特征测试、冒烟用例、接口回归用例                 | 重构前后用例全部通过      |
| 扫描巨型类/巨型方法 | 用 SonarQube、IDE 指标、CodeQL 找长方法、大类、高复杂度函数 | 单方法行数、复杂度下降     |
| 扫描命名与注释    | 让 AI 标记无意义命名、失效注释、缺失契约说明                 | 命名可读性提升，关键逻辑有说明 |
| 识别嵌套地狱     | 让 AI 列出嵌套 >3 层的函数，并给出卫语句/策略改写            | 分支覆盖率不下降        |
| 提取硬编码      | 让 AI 扫描魔法数字、URL、状态值、阈值，收敛到配置或常量          | 多环境切换不再改代码      |
| 收敛重复代码     | 让 AI 聚类重复片段，提出公共方法/组件/工具类方案              | 重复率下降，调用方行为不变   |
| 治理散落 SQL   | 让 AI 梳理数据访问点，收敛到 Mapper/Repository 层     | SQL 位置集中，可统一审计  |
| 统一异常处理     | 让 AI 扫描空 catch、吞异常、缺失日志，统一错误码和日志字段       | 故障可定位，日志字段一致    |
| 明确事务边界     | 让 AI 识别大事务、外部调用入事务、长事务                   | 事务范围缩小，无新增死锁    |
| 梳理分层边界     | 让 AI 检查 VO/DTO/Entity 混用、Service 越权调用    | 分层职责清晰，跨层调用减少   |
| 绘制模块依赖图    | 让 AI 生成包/模块依赖关系，识别循环依赖                   | 循环依赖数量下降        |
| 解耦全局状态     | 让 AI 扫描静态变量、全局可变状态，改为注入或局部状态             | 并发风险点减少         |
| 收敛配置项      | 让 AI 抽取环境、开关、阈值，形成配置清单                   | 配置变更可追踪、可回滚     |
| 评估变更影响面    | 每次改动前让 AI 列出受影响接口、表、任务、消息消费者             | 回归范围明确          |
| 补充测试安全网    | 对难以隔离的模块先补集成测试/端到端测试                     | 改动后有自动化兜底       |
| 小步重构       | 每次只改一个职责、一个类、一个分支                        | 每次提交可回滚         |
| 双跑对账       | 对资金、订单、状态机等关键逻辑做新旧实现对比                   | 输出一致才合并         |
| 记录重构决策     | 让 AI 生成变更说明：为什么改、改了什么、风险点、回滚方式           | 后续维护可追溯         |
| 持续度量       | 每次迭代后重新跑扫描，观察复杂度、重复率、依赖健康度               | 指标持续改善          |

### 建议的执行顺序

1. **第 1 周：先建安全网**  
   补关键接口回归用例、特征测试、日志观测点。

2. **第 2 周：先画地图**  
   让 AI 输出模块依赖、调用链、数据流向、外部依赖清单。

3. **第 3–4 周：先改低风险项**  
   命名、注释、硬编码、重复代码、异常处理。

4. **第 5 周起：再动高风险项**  
   巨型方法拆分、事务边界、模块解耦、分层重构。

5. **每次合并前：必须验证**  
   编译通过、测试通过、日志正常、关键指标不恶化。

### 可以直接交给 AI 的提示词模板

- “请分析这个模块的职责边界，输出当前调用链、外部依赖和潜在风险点。”
- “请列出这个文件中嵌套超过 3 层的函数，并给出等价改写方案。”
- “请扫描所有硬编码常量，按‘可配置 / 应提取为常量 / 需保留’分类。”
- “请找出重复代码簇，并说明每处差异是否可能是业务规则。”
- “请生成一组特征测试，用于锁定当前方法的输入输出行为。”
- “请把这次重构的变更范围、风险点、回滚方式整理成合并说明。”

这套清单可以当成每次迭代的“重构前检查表”。如果项目特别老，建议先从**日志、测试、配置收敛**开始，不要一上来就拆核心业务类。
