“屎山代码”不是单纯指代码丑，而是：**架构混乱、可读性差、耦合严重、修改风险高，且越改越容易出问题**。 可以从四个层面看它的特征。

### 1. 代码层面的特征

| 特征 | 典型表现 | 影响 |
|---|---|---|
| 巨型类/巨型方法 | 一个 Service 几千行，一个方法几百行，职责混杂 | 难以阅读，难以定位问题 |
| 命名随意 | `a`、`temp`、`flag1`、`doSomething` 等无意义命名 | 看名字不知道在干什么 |
| 注释缺失或失效 | 复杂逻辑没有说明，或出现“千万别动”“TODO 三年未修” | 只能靠猜前任意图 |
| 嵌套地狱 | if-else、for、回调嵌套过深 | 分支多、路径复杂、容易漏改 |
| 硬编码/魔法数字 | URL、状态值、阈值、SQL 直接写死 | 配置调整困难，容易误改 |
| 代码重复 | 相同逻辑复制粘贴到多个地方 | 改一处要同步改多处 |
| SQL 散落 | 拼接 SQL 散落在业务代码中 | 难以统一管理、优化和排查 |
| 异常处理混乱 | 吞掉异常、不打印日志、catch 后什么都不做 | 故障难排查 |
| 事务边界不清 | 大事务、超长事务、业务和数据库操作混在一起 | 性能差、死锁风险高 |
| 分层混乱 | VO/DTO/Entity 不分，业务、数据库、第三方调用纠缠 | 模块边界失效 |

### 2. 架构层面的特征

- **模块耦合严重**：改订单状态，可能影响支付、消息、定时任务。
- **职责不清晰**：一个类既处理业务，又发 MQ，又跑定时任务。
- **全局状态滥用**：静态变量、全局变量到处共享，并发场景缺少同步。
- **依赖方向混乱**：上层依赖下层、下层又反向依赖上层，形成循环依赖。
- **配置和代码混在一起**：环境、开关、阈值没有收敛到配置中心或常量管理。

### 3. 开发维护层面的信号

- **新人上手极慢**：没有架构图、业务流程图，接口文档残缺或过时。
- **团队有“修改恐惧症”**：能不动就不动，怕小改动引发线上故障。
- **牵一发而动全身**：改一个小逻辑，回归测试范围很大。
- **很难写单元测试**：依赖太多，无法隔离逻辑，只能启动完整项目调试。
- **需求靠打补丁**：不重构，只加 if 分支、临时逻辑，技术债越堆越多。

### 4. 可量化的判断指标

可以用代码分析工具看这些维度：

- **循环复杂度高**：if、for、switch、&&、|| 过多。
- **函数过长**：单方法行数明显超标。
- **嵌套过深**：超过 3–5 层嵌套。
- **代码重复率高**：相似代码块反复出现。
- **注释覆盖率低**：关键逻辑缺少说明。
- **错误处理缺失**：忽略异常、未处理返回值。
- **模块耦合度高**：包/类之间依赖复杂、循环依赖多。

一个比较实用的经验判断：**如果代码特征、维护信号、量化指标里命中 3 条以上，基本就可以认为项目已经接近或进入“屎山”状态。**

面试或复盘时可以这样概括：  
**屎山项目的本质不是“代码丑”，而是“可维护性崩塌”——读不懂、改不动、测不了、扩不开。**
